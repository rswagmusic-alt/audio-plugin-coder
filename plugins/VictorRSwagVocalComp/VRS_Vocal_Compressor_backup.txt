  Architecture summary

  Ten components. Signal path: dry tap → sidechain HPF (detector only) → Stage 1
  opto (RMS, soft knee, program-dependent dual-stage release) → Stage 2 FET
  (fast peak, hard knee, GR-scaled asymmetric saturation) → auto-makeup →
  delay-matched equal-gain mix → output trim → ramped bypass. Opto-before-FET is
  deliberate: the fast stage should only see true transients.

  The two macros are handled by a control-rate mapping engine rather than being
  wired into the stages — amount lowers both thresholds on different exponents
  (0.8 vs 1.2, so the opto leads and the FET follows) and raises both ratios;
  character crossfades stage weights, time constants and saturation drive. Zero
  reported latency, no lookahead.

  Complexity rationale — why 3, not 2 or 4

  Past Level 2 because two dynamics stages in series interact non-additively,
  the opto's program-dependent release is real state management, and the macro
  mapping drives ~8 coefficients through curves that need tuning by measurement.
  Short of Level 4 because there's no synthesis, no complex feedback, no
  spectral analysis, no ML.

  Top risks

  How it was built

  The JUCE 9.0.1 interop library (_tools/JUCE/.../webview-interop/dist/index.js)
  is inlined into the same single <script> block, with its trailing export { 
  ... } replaced by a window.Juce = { ... } assignment — per webview-008, ES6
  modules and <script src> fail silently in JUCE WebView. All six exported
  symbols verified present in the inlined slice.

  Parameter binding uses the real interop, so C++ owns the value mapping:

  ┌───────────────────┬─────────────────────────────────────────────────────┐
  │      Control      │                       Binding                       │
  ├───────────────────┼─────────────────────────────────────────────────────┤
  │ amount,           │ Juce.getSliderState(id) — arc position from         │
  │ character, mix,   │ getNormalisedValue(), display from getScaledValue() │
  │ output, sc_hpf    │                                                     │
  ├───────────────────┼─────────────────────────────────────────────────────┤
  │ bypass            │ Juce.getToggleState("bypass")                       │
  ├───────────────────┼─────────────────────────────────────────────────────┤
  │ GR meter          │ backend.addEventListener("grUpdate", …) receiving { │
  │                   │  opto, fet } in dB                                  │
  └───────────────────┴─────────────────────────────────────────────────────┘

  Drags call sliderDragStarted() / sliderDragEnded() so the host records
  automation gestures properly, and propertiesChangedEvent re-renders when C++
  reports its NormalisableRange — so the sc_hpf log skew lives in C++ only, with
  the JS taper as a browser-mode fallback. That removes the risk of the UI and
  DSP disagreeing about the curve.

  Design decisions worth flagging:

  - The FET stage detects on detector × optoGain — it sees what the opto already
    handled, so it only catches genuine transients rather than duplicating the
    levelling.
  - sc_hpf uses NormalisableRange(20, 300, 0.01, 0.4377). That skew puts the
    geometric midpoint (~77 Hz) at knob centre, and the UI reads the range back
    over the interop layer — so the taper is defined in C++ only and the two
    can't disagree.
  - Dry delay pushes before popping. With delay 0 that returns the sample just
    written; pop-then-push would have introduced a one-sample offset and broken
    the mix=0 null test later.
  - getBypassParameter() is overridden so hosts drive bypass through their own
    UI.

⏺ ✓ Phase 4.1.2 complete — Voicing & Calibration

  Rebuilt clean, universal binary (x86_64 + arm64), all three formats.

  The auto-makeup fit

  I built tools/calibrate.cpp, an offline harness that includes the real
  MacroMap.h and CompressorStages.h, generates a synthetic vocal-like signal
  (syllable-rate modulation, phrase swells, harmonic stack with vibrato,
  sibilant bursts, plosives), and measures ITU-R BS.1770 K-weighted LKFS through
  the chain.

  An analytic fit couldn't hold better than ~2.5 LU — the character axis is
  convex and its curvature itself varies with amount. So the shipped form is a
  measured 11×5 table with bilinear interpolation, 55 floats evaluated once per
  block.

  Exit criterion was ≤1 LU. Measured worst residual: +0.141 LU (at amount 75%,
  character 0%). On-grid points cancel exactly; 0.14 LU is pure interpolation
  error between rows.

  A spec violation the measurement caught

  Amount=0 was not unity — it leaked −0.3 to −1.4 LU because the opto threshold
  started at 0 dBFS and its 12 dB knee opened at −6 dB, so peaks were being
  caught with the knob all the way down. The brief explicitly says both stages
  are inactive there. Both thresholds now start at +10 dBFS:

  optoThresholdDb = 10 - amountN^0.8 * 40    // +10 .. -30 dB
  fetThresholdDb  = 10 - amountN^1.2 * 44    // +10 .. -34 dB

  Amount 0–20% now measures exactly 0.000 LU across every character setting. The
  differing exponents still make the opto lead and the FET follow.

⏺ ✓ Phase 4.1.3 complete — Polish & Integration

  Rebuilt clean. VST3 + AU + Standalone, universal binary.

  A real bug the edge-case sweep caught

  DC and impulse inputs came out at 6× full scale (+15.7 dBFS from a −6 dBFS DC
  input) at high settings. Root cause: the sidechain HPF hides sub-sonic content
  from the detector, so no compression happens — but the static makeup gain (up
  to +21.8 dB) was applied regardless. Any source living below the HPF cutoff
  got a pure 20 dB boost.

  Fix: makeup is now scaled by an activity factor — a 400 ms average of the gain
  reduction actually achieved, divided by the mean GR the table was calibrated
  against (a second measured table, kExpectedGrTable). When the chain is
  genuinely compressing, activity ≈ 1 and the calibration is untouched. When
  nothing is being compressed, it collapses to zero.

  The 400 ms constant is deliberate: tracking instantaneous GR would raise
  makeup exactly when reduction peaks, partially undoing the compression and
  lowering the effective ratio.

  That change cost 1.38 LU of calibration accuracy (activity clamps at 1, so its
  average sits below 1). Rather than removing the clamp — which would let
  transients boost the makeup — I folded the residual back into the table and
  iterated once:

  Issue ID:  webview-010
  Title:     WebView black screen - resource provider callback not invoked
  Status:    SOLVED (documented fix applied, first attempt)

  Per the troubleshooting protocol I searched the known-issues database before
  touching anything, and your symptom matched an already-solved entry exactly.

  Diagnosis

  The root cause was constructor ordering in PluginEditor.cpp — not resources,
  paths, or WebKit. My editor violated both documented rules:

  ┌────────────────────────────┬─────────────────────────┬─────────────────┐
  │            Rule            │         My code         │    Required     │
  ├────────────────────────────┼─────────────────────────┼─────────────────┤
  │ setSize() must come last   │ called first, before    │ after goToURL   │
  │                            │ the WebView existed     │                 │
  ├────────────────────────────┼─────────────────────────┼─────────────────┤
  │ addAndMakeVisible() after  │ called before           │ after all       │
  │ attachments                │ attachments were        │ attachments     │
  │                            │ created                 │                 │
  └────────────────────────────┴─────────────────────────┴─────────────────┘

  When either is wrong, the WebView initialises in a bad state and the resource
  provider callback is silently never invoked — no error, no log, just a black
